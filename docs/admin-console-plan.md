# 树莓社「内部操作页」分析与方案设计 v3（中间开关层版）

> 日期：2026-09-06 v3 ｜ 基线：worker.js @ ba1377f
> v1（重型管理台）→ v2（飞书列开关）→ **v3（网页中间开关层）**，根据三轮需求澄清收敛：
> ① 看 KV（只读）② 一键全量刷新 ③ **字段级隐私开关，在网页上点，开关独立存放（中间层），不在飞书加列**；`members_full`（App 全量快照）豁免过滤（已确认）。

---

## 一、结论

**网页中间开关层可行，且是三个存储方案里最合适的**。核心结论先讲清楚：

> **网页开关必须有一个"持久化位置"，且只有两个现实候选：飞书加列（你已否决）或 KV 新增一个小 key。**
> 选了网页开关 = 开关状态存 KV 新 key；这只"加一个 key"，**不改动**现有 6 个 KV key、不提供任何"直接改 KV"的页面能力（你的"不改动 KV"理解为：不把 KV 当操作对象，KV 只是开关的储物柜——它本来就是 Worker 的持久层）。

理由：Cloudflare 上这个 Worker 的持久化手段只有 KV（无数据库）。飞书列方案与网页开关方案二选一，中间开关层的全部代码增量约 **+1 个 KV key、+1 个管理端点、detail 输出 ~10 行过滤、admin.html 一个开关 tab**。

---

## 二、三个功能最终形态（v3）

### 功能 ①：看 KV（只读）

- `GET /api/admin/kv/list` → 键名 / 条数 / 体积 / updatedAt / 健康
- `GET /api/admin/kv?key=xxx` → 格式化 JSON 查看
- 敏感字段（members_full 的「登录密码」等）默认打码 `***`，二次确认 `&reveal=1` 才返回原文
- 只读不改——与 v2 一致，不提供删除/写入按钮

### 功能 ②：网页一键全量刷新

- admin.html 大按钮「一键全量刷新」→ 触发**现有** `POST /api/refresh`（全量重建 4 快照，与自动化同口径）
- 页面回显各快照条数 + updatedAt + 耗时，按钮带 30s 冷却倒计时
- 鉴权：页面登录用 `ADMIN_TOKEN`；`handleRefresh` 改为**同时接受 REFRESH_TOKEN 或 ADMIN_TOKEN**（改动 1 行），页面只记一个口令即可刷新

### 功能 ③：字段级隐私开关 ——「中间开关层」（本次核心变化）

**语义**：某社员 × 某字段（如「升学去向」）在网页上关掉 → 所有 API 响应中该字段输出 `""`，与"此人没填这个字段"完全一致 → 下游拿不到。

**存储与流向**：

```
admin.html 开关面板
   │ 选择社员 + 勾选要隐藏的字段（升学去向 / 详细介绍 / …）
   ▼
POST /api/admin/field-visibility（Bearer ADMIN_TOKEN，新增）
   │ 写 KV 新 key：field_hidden_v1 = { 识别码: ["grad","bio",…], updatedAt }
   │ 顺手 cache.delete 该社员 detail 的边缘缓存 → 立即生效（不等 5 分钟）
   ▼
Worker 读接口（/api/members/detail）
   ① 先查 field_hidden_v1 里该识别码的隐藏字段（内存 30s 缓存，零额外 KV 压力）
   ② 命中隐藏的字段 → 输出置 ""（与没填一致）
   ③ members_full / members / member / checkin / avatar 等一律不看开关（全量豁免已确认）
```

**要点**：

| 问题 | 答案 |
|---|---|
| 开关存哪 | KV 新 key `field_hidden_v1`（唯一现实持久层；不动现有 6 key，不提供改 KV 界面） |
| 影响哪些接口 | **仅 `/api/members/detail`**（公开档案展示面）。查人接口不含这些字段；App 快照豁免 |
| 表现形态 | 字段输出 `""`，与没填完全一致（不是删字段、不是报错） |
| 可开关字段清单 | 由 detail 的展示字段限定，先试点：`升学去向 grad` / `详细介绍 bio` / `其他职务或荣誉 honor` / `别名 alias`（可扩展，页面自动读固定清单） |
| 生效速度 | 保存时主动失效该社员 detail 边缘缓存 → 下一个请求即生效；网络兜底最多 5 分钟（detail TTL） |
| 性能影响 | detail 每请求查一次内存缓存（30s 有效期），**零 KV 读取压力** |
| 操作对象 | 按社员识别码定位（页面用现有 /api/members 映射选人，或直接输识别码） |

## 三、为什么这是最优解（候选对比）

| 方案 | 飞书加列 | **KV 中间开关层（v3 推荐）** | 网页直改飞书字段 |
|---|---|---|---|
| 飞书表负担 | ❌ 每个可开关字段加一列，字段一多表就臃肿 | ✅ 零新增列 | ✅ 零新增列 |
| 网页操作 | ✅（改飞书） | ✅ 专用开关面板 | ✅ |
| 代码改动 | detail 读列过滤 | +1 key +1 端点 +detail 过滤 | +1 端点写飞书（需写权限） |
| 状态一致性 | 开关=数据，天然一致 | 独立存储，靠端点维护 | 开关=数据 |
| 风险 | 表结构膨胀（你已否决） | 开关与数据分离（小，30s 内一致） | 需确认飞书 app 写权限 + 每次写飞书有配额成本 |
| 你的约束 | ✗ | ✅ 不改 KV 语义（仅新增小 key 储物） | 同左但更重 |

**结论**：网页开关 + KV 小 key 是最小代码路径；若未来想彻底去掉 KV 依赖，再把开关迁回飞书列即可（过滤逻辑同构，只换数据源）。

## 五、风险与注意

1. **开关粒度 = 社员 × 字段**；每个社员存的是一串字段名（如 `["grad"]`），总量极小（几百人 × 几个字段名 ≈ 几 KB）。
2. **缓存一致性**：保存开关时主动 `cache.delete` 该社员 detail 缓存条目（构造 key 与 detail 处理器同源，`https://<host>/_cache/detail/<code>`）——这是让开关"秒级生效"的关键一步；若漏删，最多 5 分钟自然过期兜底。
3. **豁免面已确认**：members_full（App 快照）、members（H5 离线映射）、member（签到查人）、avatar/photo/file/activities 全都不读开关。
4. 安全：管理端点统一 Bearer `ADMIN_TOKEN`（新 Secret），与 REFRESH_TOKEN 双 token 方案二选一（建议直接双 token 各自独立，页面只存 ADMIN_TOKEN）。
5. field_hidden_v1 会随 refresh 被重写吗？**不会**——refresh 只重建 4 个快照 key，开关 key 独立、永久保留，直到有人在页面改。
